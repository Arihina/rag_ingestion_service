# Разведение портов

Сервис слушает **два порта** с разным набором ручек и разной сетевой
доступностью. Это единственный барьер вокруг служебных эндпоинтов после
того, как из реализации убран общий API-ключ.

---

## Что вообще значит «развести порты»

Одна и та же программа может слушать несколько TCP-портов. Обычно так
делают не ради удобства, а чтобы **доступ к разным группам ручек можно было
ограничивать разными средствами**: файрволом, правилами Docker, настройками
прокси. Пока всё висит на одном порту, любое правило действует на всё
сразу — либо открыто всем, либо закрыто всем.

Полезно различать три вещи, которые часто путают.

**Адрес прослушивания (bind).** На каком интерфейсе процесс ждёт
соединений внутри своего сетевого пространства. `127.0.0.1` — только с той
же машины (или из того же контейнера), `0.0.0.0` — с любого интерфейса.

**Публикация порта.** Правило Docker `-p 127.0.0.1:8011:8011`, которое
пробрасывает порт контейнера на хост. Непубликованный порт всё равно
доступен соседям по сети compose — просто не виден снаружи.

**Сетевая достижимость.** Кто физически может открыть соединение: соседний
контейнер, другая машина, интернет.

Отсюда неочевидное следствие, на которое легко напороться: **привязка к
`127.0.0.1` внутри контейнера отрезает не «внешний мир», а вообще всех,
включая соседние контейнеры** — у каждого контейнера свой `localhost`.
Чтобы воркер из другого контейнера достучался до внутреннего порта, тот
обязан слушать `0.0.0.0`, но при этом **не публиковаться** на хост.
Именно так настроен `docker-compose.dev.yml`.

## Как разведено у нас

| | Платформенный | Внутренний |
|---|---|---|
| Порт | 8011 | 8012 |
| Ручки | `/health`, `/v1/platform/*` | `/health`, `/embed`, `/v1/internal/*`, `/admin/*` |
| Кто ходит | `master_node` | `agentic_rag`, воркеры, оператор |
| Публикуется | да | **нет** |

Приложений два (`app` и `internal_app` в `app/main.py`), процесс один. Один
процесс — потому что модель bge-m3 существует в единственном экземпляре на
пару пулов, и второй процесс поднял бы вторую копию с независимыми
семафорами к той же карте.

`/health` есть на обоих: живость проверяют и мастер, и оркестратор
контейнеров, а разводить это по разным адресам смысла нет.

---

## Почему каждая ручка там, где она есть

**`/v1/platform/*` — снаружи.** Здесь всё скоупится по `X-User-Id`, и
доступ к чужому набору даёт `404`. Это ручки конечного пользователя,
проксируемые мастером.

**`/embed` — внутрь.** Прямой доступ к GPU. Любой, кто до него дотянется,
одним циклом положит латентность чата всей платформы: очередь к карте
общая. Аутентификация тут ни при чём — важна именно недостижимость.

**`/v1/internal/*` — внутрь.** Принимает `user_id` **параметром запроса** и
по нему отдаёт конфиг набора. Проверка владения здесь есть, но она
доверяет переданному значению: подставив чужой UUID, вызывающий получит
чужой конфиг. На платформенном порту это было бы дырой, на внутреннем —
осознанным доверием между сервисами.

**`/admin/*` — внутрь.** Импортирует файлы в произвольный набор без
проверки владельца и показывает содержимое staging.

Путь `/admin` намеренно **не** начинается с `v1/`: catch-all мастера
форвардит любой путь под `v1/` без разбора, и `/v1/admin/...` уехал бы
наружу автоматически, даже стоя на другом порту, если бы кто-то ошибся с
адресом апстрима.

## Настройка

```
INGEST_HOST=127.0.0.1          # платформенный
INGEST_PORT=8011
INGEST_INTERNAL_HOST=127.0.0.1 # внутренний
INGEST_INTERNAL_PORT=8012
INGEST_SELF_URL=http://localhost:8012   # куда воркер ходит за векторами
```

`INGEST_SELF_URL` обязан указывать на **внутренний** порт: `/embed` на
платформенном отсутствует. Несовпадение даёт `404` на каждой задаче
индексации.

### Дев на хосте

Оба порта на `127.0.0.1`, всё на одной машине — этого достаточно.

### Дев в контейнерах

```yaml
api:
  environment:
    INGEST_HOST: 0.0.0.0
    INGEST_INTERNAL_HOST: 0.0.0.0     # иначе воркер не достучится
    INGEST_SELF_URL: http://api:8012
  ports:
    - "127.0.0.1:8011:8011"           # 8012 НЕ публикуется
```

### Прод

Ни один порт наружу не публикуется, оба объявлены через `expose`. Доступ к
8011 — только у мастера, к 8012 — у сервисов платформы. Если мастер живёт
вне сети compose, публиковать нужно **только** 8011 и только на тот
интерфейс, откуда он ходит.

### Один порт вместо двух

```
INGEST_INTERNAL_PORT=0
```

Все ручки вешаются на платформенный порт. Сервис пишет предупреждение в
лог при старте. Допустимо только когда до сервиса физически не дотянуться
ни с одной чужой машины — например, всё на ноутбуке разработчика. В любом
развёртывании, где есть сеть, это открывает `/admin` и `/embed` всем, кто
видит платформенный порт.

## Проверка

Состав ручек на каждом порту:

```bash
curl -s localhost:8011/openapi.json | jq -r '.paths | keys[]'
curl -s localhost:8012/openapi.json | jq -r '.paths | keys[]'
```

Служебных ручек на 8011 быть не должно:

```bash
curl -s -o /dev/null -w "%{http_code}\n" localhost:8011/embed          # 404
curl -s -o /dev/null -w "%{http_code}\n" localhost:8011/admin/staging  # 404
```

Из контейнера — что внутренний порт достижим соседям, но не хосту:

```bash
docker compose -f docker-compose.dev.yml exec worker \
  sh -c 'wget -q -O- http://api:8012/health && echo OK'
curl -s --max-time 2 localhost:8012/health || echo "снаружи недоступен — так и надо"
```

То же самое покрыто тестами `PortSeparationTests` в
`tests/test_api_rags.py`: они проверяют состав ручек каждого приложения и
что `INGEST_SELF_URL` указывает на внутренний порт.

## Чего разведение портов не решает

Стоит проговорить, чтобы не возникло ложного ощущения защищённости.

**`X-User-Id` остаётся доверенным.** Любой, кто дотянулся до
платформенного порта, представляется кем угодно и читает чужие документы.
Разведение портов сужает круг тех, кто может дотянуться, но не проверяет,
кто именно пришёл. Снимается это только Keycloak: `auth.py` начинает
валидировать JWT, `user_id` берётся из `sub` токена.

**Внутри сети барьеров нет.** В той же сети живёт docling, который по
устройству ходит по произвольным URL, и Dashboards с веб-интерфейсом.
Компрометация любого из них даёт доступ к 8012.

**Разграничения прав между внутренними сервисами нет.** Воркеру нужен
только `/embed`, а доступен весь внутренний порт целиком.

Все три — известные ограничения текущего этапа, а не недосмотр. Первое
закрывается Keycloak, второе и третье — сетевыми политиками, если
понадобятся.

## Почему не API-ключ

Он был и убран. Аутентификацией он не являлся: один общий секрет на всех
вызывающих не различал, кто пришёл, и не мешал представиться чужим
`X-User-Id`. Закрывал ровно один сценарий — случайно опубликованный порт,
— то есть ту же задачу, что решает разведение портов, но ценой секрета,
который надо раздать четырём сервисам, хранить и ротировать.

Отдельно он тянул за собой механику в мастере: `proxy()` умеет отдавать
агенту только `X-User-Id` и `Content-Type`, и статический заголовок
пришлось бы прокидывать через реестр — с новым полем в `AgentInfo` и новым
инвариантом (заголовки из реестра не должны позволять переопределить
`X-User-Id`, иначе через реестр подменяется пользователь). Слабый секрет
породил бы механизм с собственной поверхностью для ошибок.

Ключ docling (`INGEST_DOCLING_API_KEY`) к этому отношения не имеет: это
чужой сервис со своей схемой, и его мы просто предъявляем.
