# RAG Ingest: docling → bge-m3 → OpenSearch

Конвейер подготовки базы знаний. Документы любых форматов превращаются в чанки
с сохранённой структурой и провенансом, векторизуются и попадают в OpenSearch,
готовые к гибридному поиску.

```
             └──────┬───────┘

        ▼                        ▼
┌───────────────┐        ┌───────────────┐
│ docling-serve │        │    bge-m3     │
│ parse+chunk   │        │ dense+sparse  │
│    (GPU)      │        │    (GPU)      │
└───────┬───────┘        └───────┬───────┘
        │      чанки             │  векторы
        └───────────┬────────────┘
                    ▼
            ┌───────────────┐
            │  OpenSearch   │
            │ BM25 + kNN +  │
            │ rank_features │
            └───────────────┘
```

### Роли компонентов

**docling-serve** закрывает стадии Parse, Structure и Chunk. На выходе —
`DoclingDocument`: дерево с заголовками, таблицами и списками, где у каждого
элемента есть провенанс (номер страницы, bbox). Дальше HybridChunker режет это
дерево с учётом токенизатора эмбеддера: не разрывает таблицы, склеивает мелкие
соседние блоки, добавляет к каждому чанку родительские заголовки.

**bge-m3** считает из одного прохода плотный вектор (1024 измерения) и
разреженные лексические веса. Второй выход — готовая замена SPLADE для третьей
ветки гибридного поиска, без отдельной модели.

**OpenSearch** хранит три представления каждого чанка: текст под BM25 с русской
морфологией, плотный вектор в HNSW и разреженные веса в `rank_features`.

## Требования

### GPU

Обе целевые карты покрываются одним образом `docling-serve-cu128`, поэтому дев и
прод собираются из одного билда.

| | Dev | Prod |
|---|---|---|
| Карта | RTX 5070 Ti | A100 |
| Архитектура | Blackwell, `sm_120` | Ampere, `sm_80` |
| Минимум CUDA | 12.8 | 11.0 |
| VRAM | 16 ГБ | 40/80 ГБ |

**Важно про 5070 Ti.** Blackwell требует сборок PyTorch не ниже CUDA 12.8. Образ
на cu121 или cu124 запустится, отработает инициализацию и упадёт на первом
forward с `no kernel image is available for execution on the device`. Ошибка
выглядит как поломка драйвера, хотя это несовпадение архитектуры.

Потребление VRAM стандартным пайплайном docling скромное — layout (RT-DETR) плюс
TableFormer укладываются в 3–4 ГБ. bge-m3 в fp16 добавляет около 1.5 ГБ. На
16 ГБ помещается с запасом, на A100 остаётся место под несколько воркеров.

### Софт

- Docker с nvidia-container-toolkit
- Python 3.11+ для загрузчика

```bash
pip install httpx opensearch-py FlagEmbedding \
            fastapi uvicorn pydantic-settings python-multipart
```

## Быстрый старт (dev)

```bash
docker compose -f docker-compose.dev.yml up -d --build
```

Первая сборка долгая: качаются веса docling (~2–3 ГБ) и токенизатор bge-m3.
Слой с весами стоит выше остальных в `Dockerfile`, поэтому последующие правки
кэш не сбрасывают.

Проверка:

```bash
curl -s localhost:9200/_cluster/health | jq .status
curl -s localhost:5001/health
```

Дев-инстанс docling поднят с UI на <http://localhost:5001/ui> — туда можно
закинуть проблемный PDF руками и посмотреть, что вернули layout и OCR, не гоняя
пайплайн целиком. Dashboards на <http://localhost:5601>.

Загрузка корпуса напрямую, без HTTP-слоя:

```bash
python rag_ingest.py
```

Или через API:

```bash
uvicorn ingest_api:app --port 8000
curl -X POST localhost:8000/ingest/file -F "file=@doc.pdf"
```

## Продакшен

```bash
cp .env.example .env   # DOCLING_KEY, OPENSEARCH_PASSWORD, DOCLING_IMAGE
docker compose -f docker-compose.prod.yml up -d
```

### Отличия от дева

Образ не собирается, а приезжает из реестра — в `docker-compose.prod.yml` нет
секции `build`. Пинить лучше по digest, а не по тегу: тег можно молча
перезаписать, digest нельзя.

```yaml
image: registry.internal/docling-serve@sha256:abc123...
```

Конверсия уходит в очередь: API ставит задачи в Redis, а работу выполняют
процессы `docling-serve rq-worker`. `DOCLING_SERVE_ENG_RQ_REDIS_URL` обязан
совпадать во всех процессах. **API без единого воркера принимает задачи, но
никто их не выполняет** — снаружи это выглядит как вечный `pending`.

`HF_HUB_OFFLINE=1` гарантирует, что в рантайме ничего не полезет в сеть. Все
веса уже в образе.

### Стоит ли держать OpenSearch тут же

В `docker-compose.prod.yml` он включён, потому что файл задумывался
самодостаточным. Но `single-node` без реплик означает, что потеря диска равна
потере индекса, а поиск и парсинг конкурируют за память и IO совершенно
по-разному. Если кластер уже живёт отдельно — выбрось сервис `opensearch` и
оставь docling с Redis.

### Сколько воркеров

Три реплики в файле — стартовая догадка, не рекомендация. Померь на своём
корпусе: если документы преимущественно текстовые PDF без OCR, узкое место
окажется на CPU, и упрёшься ты в `DOCLING_NUM_THREADS`, а не в карту. Тогда
выгоднее меньше реплик с большим числом потоков каждая.

## Конфигурация

### docling-serve

| Переменная | Назначение |
|---|---|
| `DOCLING_SERVE_ARTIFACTS_PATH` | Каталог локальных весов; включает офлайн-режим |
| `DOCLING_DEVICE` | `cpu`, `cuda`, `cuda:0`, `mps` |
| `DOCLING_NUM_THREADS` | Потоки CPU-исполнения torch |
| `DOCLING_SERVE_ENG_KIND` | `local` или `rq` |
| `DOCLING_SERVE_ENG_RQ_REDIS_URL` | Обязателен при `rq`, одинаков во всех процессах |
| `DOCLING_SERVE_API_KEY` | Включает проверку заголовка `X-Api-Key` |
| `DOCLING_SERVE_ENABLE_UI` | Gradio-интерфейс на `/ui` |

При `--reload` или `--workers > 1` uvicorn плодит подпроцессы, и CLI-флаги
игнорируются. В таких развёртках всё настраивается только через переменные
окружения — поэтому в compose-файлах нет `command` с флагами.

### OCR и русский язык

RapidOCR работает на моделях PP-OCR. Кириллица есть в PP-OCRv4 (`cyrillic`) и
PP-OCRv5 (`cyrillic`, `eslav`), **а в PP-OCRv6 её нет вообще**.

Для русских документов бери `eslav` — восточнославянская группа
(русский, белорусский, украинский, английский). Это заметно точнее, чем общий
`cyrillic` на 34 языка: чем уже набор, тем меньше модель путает похожие глифы.

Отдельного PaddleOCR-движка в docling нет. Paddle присутствует как бэкенд внутри
RapidOCR наряду с `onnxruntime`, `openvino` и `torch`. Модели в любом случае
паддловские, так что выбор бэкенда — это выбор рантайма, а не качества.
`onnxruntime` (по умолчанию) избавляет от зависимости `paddlepaddle` весом
~700 МБ и отдельной возни с совместимостью CUDA.

Если PDF заведомо текстовые, `do_ocr=false` экономит львиную долю времени.

## HTTP API

### `POST /ingest/file`

Multipart-загрузка. Отвечает `202` сразу — конверсия PDF занимает секунды на
страницу, держать соединение открытым незачем.

```bash
curl -X POST localhost:8000/ingest/file \
  -H "X-Api-Key: $KEY" \
  -F "file=@report.pdf"
```

```json
{"job_id": "a3f...", "filename": "report.pdf", "status": "pending", "chunks_loaded": 0}
```

### `GET /ingest/status/{job_id}`

```json
{"job_id": "a3f...", "status": "success", "chunks_loaded": 47, "error": null}
```

Реестр задач живёт в памяти процесса и не переживает рестарт. Для durable-очереди
подключай тот же Redis, что и docling-serve.

### `POST /embed`

Векторизация тем же экземпляром модели, что обрабатывал документы.

```bash
curl -X POST localhost:8000/embed \
  -H "Content-Type: application/json" \
  -d '{"texts": ["порядок расторжения договора"]}'
```

Этот эндпоинт решает главную проблему отказа от ML Commons. Когда вектор запроса
считает клиент, ничто не мешает ему однажды посчитать его чуть иначе: другая
версия модели, другой пулинг, забытая нормализация. Ошибка не выдаст
исключения — она просто просадит выдачу, и причину будешь искать в настройках
HNSW. Один эндпоинт на всю систему делает такое расхождение невозможным.

**Префиксы не нужны.** bge-m3 обучалась без инструкций — никаких `query:` и
`passage:`, в отличие от e5. Забытый от e5 префикс не даст ошибки, он тихо
просадит качество на несколько пунктов NDCG.

### `GET /health`

Проверяет доступность docling и OpenSearch. `degraded`, если что-то из этого
недоступно.

## Структура индекса

```
source_uri      keyword       путь или URL исходника
chunk_index     integer       порядковый номер чанка
content         text/ru_en    BM25 с русской морфологией
headings        text/ru_en    цепочка родительских заголовков
pages           integer[]     страницы исходника — для цитирования
content_hash    keyword       хэш содержимого, для skip_unchanged
content_vector  knn_vector    1024 dim, HNSW/faiss, cosinesimil
content_sparse  rank_features lexical_weights из bge-m3
```

### Почему 1024, а не 384

Переход с multilingual-e5-small на bge-m3 меняет размерность втрое, и HNSW-граф
растёт соответственно. Отсюда правки в compose:

- heap 512m → 2g в деве, 16g в проде;
- `knn.memory.circuit_breaker.limit` — HNSW-графы лежат **вне** heap, и этот
  лимит с `-Xmx` не связан.

С 384 измерениями 512m ещё как-то жило. С 1024 и bulk пачками по несколько сотен
документов упрётесь в потолок быстро и получите circuit breaker посреди загрузки.

Прод-heap считается как половина RAM ноды, но не выше ~31 ГБ: за этой границей
JVM теряет сжатые указатели, и heap начинает работать хуже, а не лучше.

### Про идемпотентность

`_id` чанка строится детерминированно как `blake2b(source_uri:chunk_index)`,
операция — `index`, а не `create`. Повторный прогон перезаписывает документы, а
не падает на конфликте и не плодит дубли.

`skip_unchanged` дополнительно сравнивает `content_hash` и пропускает
неизменившиеся чанки. Оговорка: если документ поправили в середине, все
последующие чанки сдвинутся по индексу и переиндексируются целиком. Это
корректно, но не оптимально. Для больших документов с точечными правками лучше
строить `_id` от хэша заголовков плюс содержимого — тогда сдвиг не каскадирует.

## Поиск

Три ветки, объединяемые на стороне OpenSearch. Векторы запроса берутся из
`/embed`.

```json
{
  "query": {
    "hybrid": {
      "queries": [
        { "match": { "content": { "query": "<текст>" } } },
        { "knn": {
            "content_vector": {
              "vector": [/* dense из /embed */],
              "k": 100,
              "filter": { "term": { "source_uri": "..." } }
            }
        }},
        { "bool": { "should": [
            { "rank_feature": { "field": "content_sparse.12345", "boost": 0.7 } }
        ]}}
      ]
    }
  }
}
```

Два момента, на которых легко ошибиться:

**Фильтр должен быть внутри `knn`**, а не post-filter снаружи. Иначе HNSW сначала
наберёт k соседей по всему индексу, а фильтр отрежет от них большую часть, и
выдача окажется короче ожидаемой.

**`pagination_depth` в конфиге search-пайплайна** должен быть достаточно большим,
чтобы до слияния дошло нужное число кандидатов от каждой ветки. Слишком малое
значение обрежет ветки до слияния, и RRF будет работать с обеднённым материалом.

Слияние настраивается через `score-ranker-processor` (RRF, OpenSearch 2.19+) или
`normalization-processor`. Качество меряется через `_rank_eval` по NDCG@10.

## Как файлы попадают в docling

Только по HTTP. docling-serve — stateless-сервис без файлового входа: он не умеет
смотреть в примонтированную папку и не имеет понятия «путь к документу».
Монтировать в него том с корпусом бессмысленно.

| Способ | Когда |
|---|---|
| multipart (`-F "files=@doc.pdf"`) | Файлы на диске рядом с загрузчиком. Основной путь |
| base64 в `file_sources` | Если по дороге прокси, ломающий multipart. +33% к объёму |
| `http_sources` | Файлы в S3/MinIO: presigned URL, сервис качает сам |

Третий вариант экономнее для объектного хранилища — байты не проходят через твой
процесс дважды.

## Диагностика

**`no kernel image is available for execution on the device`**
Образ собран под CUDA старше 12.8, а карта — Blackwell. Проверь базовый образ в
`Dockerfile`: нужен `docling-serve-cu128` или `cu130`.

**Задачи вечно в `pending`**
Работают только API-контейнеры, воркеры не поднялись. Проверь
`docker compose ps` и совпадение `DOCLING_SERVE_ENG_RQ_REDIS_URL` во всех
процессах.

**Чанки без заголовков в начале**
Клиент забрал не то поле ответа. `_extract_text` в `docling_client.py`
перебирает `contextualized_text` → `text` → `raw_text`, потому что имя поля
различается между версиями. Прогони один документ, посмотри на выход и поправь
порядок ключей. Полная схема всегда на `/docs` живого сервера — она авторитетнее
любой документации, включая эту.

**Границы чанков не совпадают с ожиданиями**
Не передан `chunking_tokenizer`, и HybridChunker считает токены дефолтным
токенизатором. Он должен совпадать с эмбеддером — отсюда
`ChunkingOptions(tokenizer="BAAI/bge-m3")`.

**Circuit breaker при bulk-загрузке**
Мало heap или исчерпан off-heap под HNSW. Подними `-Xmx` и проверь
`knn.memory.circuit_breaker.limit`.

**Изображения не приходят из чанк-эндпоинта**
Известное ограничение: ссылки на ассеты не возвращаются даже при
`include_images=true`. Если нужны картинки — отдельный вызов `/v1/convert/*` с
`image_export_mode=referenced`.

**Настройки OCR не влияют на результат**
Параметр `ocr_engine` объявлен устаревшим; используются `ocr_preset` и
`ocr_lang`. Актуальный список пресетов — на `/docs`.
