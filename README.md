# RAG Ingest: control plane пользовательских наборов

Сервис, в котором живут RAG-наборы: пользователь создаёт набор, заливает в него
документы, а сервис превращает их в чанки с сохранённой структурой и
провенансом, векторизует и кладёт в OpenSearch.

Две роли в одном коде:

- **control plane** — наборы, документы, задачи, конфиг. Postgres, Redis, SeaweedFS.
- **data plane на запись** — docling → bge-m3 → OpenSearch.

Читает из OpenSearch другой сервис (`agentic_rag`), и это единственная
асимметрия, которую нельзя нарушать: пишет сюда только ingest, читает только он.

## Архитектура

```
                    ┌──────────────────────────────┐
   master_node ────▶│            api               │  FastAPI
                    │  /v1/platform/rags  (CRUD)   │  владеет GPU
                    │  /v1/internal/rags  (agentic)│  2 x bge-m3
                    │  /embed             (pool)   │
                    └──┬────────┬──────────┬───────┘
                       │        │          │
          ┌────────────┘        │          └──────────────┐
          ▼                     ▼                         ▼
   ┌────────────┐        ┌────────────┐            ┌────────────┐
   │ PostgreSQL │        │   Redis    │            │ SeaweedFS  │
   │  наборы    │        │  очереди   │            │  файлы     │
   │  документы │        │  RQ        │            │  иконки    │
   └─────▲──────┘        └─────▲──────┘            └─────▲──────┘
         │                     │                         │
         │              ┌──────┴───────┐                 │
         └──────────────│    worker    │─────────────────┘
                        │  без модели  │
                        │  без GPU     │
                        └──┬────────┬──┘
                           │        │  вектора по HTTP → api:8012/embed
                           ▼        ▼
                    ┌────────────┐  ┌──────────────┐
                    │  docling   │  │  OpenSearch  │
                    │ parse+chunk│  │    kb-v2     │
                    └────────────┘  └──────────────┘
```

**docling-serve** закрывает стадии Parse, Structure и Chunk. На выходе —
`DoclingDocument`: дерево с заголовками, таблицами и списками, где у каждого
элемента есть провенанс (номер страницы, bbox). HybridChunker режет это дерево
с учётом токенизатора эмбеддера: не разрывает таблицы, склеивает мелкие
соседние блоки, добавляет к каждому чанку родительские заголовки.

**bge-m3** считает из одного прохода плотный вектор (1024 измерения) и
разреженные лексические веса. Второй выход — готовая замена SPLADE для третьей
ветки гибридного поиска, без отдельной модели.

**OpenSearch** хранит три представления каждого чанка: текст под BM25 с русской
морфологией, плотный вектор в HNSW и разреженные веса в `rank_features`.

## Две роли: api и worker

Разделение не косметическое, поэтому объясняется отдельно.

| | `api` | `worker` |
|---|---|---|
| Модель bge-m3 | два экземпляра | нет |
| torch / FlagEmbedding | да | **нет** |
| GPU | нужен | не нужен |
| Размер образа | ~6 ГБ | ~200 МБ |
| Реплик | ровно 1 | сколько угодно |

**Почему воркер не держит модель.** RQ форкается на каждую задачу. Модель,
загруженная на импорте модуля, либо переезжает в форк целиком — полторы секунды
и полтора гигабайта на каждую задачу, — либо требует `SimpleWorker` без форка, и
тогда падение одной задачи уносит воркер. Плюс GPU один, и сериализовать доступ
к нему должен ровно один набор семафоров в одном процессе: при модели в каждом
воркере три реплики конкурировали бы за карту без всякой координации.

Вместо этого воркер ходит за векторами по HTTP в `/embed` процесса `api`, передавая
`pool="ingest"`. Побочный выигрыш: воркеры масштабируются обычными контейнерами
без проброса устройств, и это единственная ручка масштабирования индексации.

**Два экземпляра модели в api.** Один обслуживает индексацию (`pool="ingest"`),
второй — запросы из чата (`pool="query"`). Веса и версия те же, поэтому вектор
запроса физически не может разойтись с вектором документа — ради этого `/embed`
и существует. Разделение нужно для другого: заливка корпуса это сотни батчей
подряд, и на общем семафоре чат ждал бы не свои 30 мс, а глубину очереди,
умноженную на время батча, и так на каждой итерации агентного цикла.

Второй инстанс стоит ~1.5 ГБ VRAM. Если её жалко —
`INGEST_SEPARATE_QUERY_EMBEDDER=false`, и оба сценария делят один экземпляр.

Отдельно: семафор индексации охватывает **только вызов модели**, а не весь
пайплайн. Если взять его вокруг всей обработки файла, он удерживался бы всё
время конверсии в docling — минуты на скан, — и `/embed` встал бы в очередь за
парсингом PDF.

## Требования

### GPU

Обе целевые карты покрываются одним образом, поэтому дев и прод собираются
одинаково.

| | Dev | Prod |
|---|---|---|
| Карта | RTX 5070 Ti | A100 |
| Архитектура | Blackwell, `sm_120` | Ampere, `sm_80` |
| Минимум CUDA | 12.8 | 11.0 |
| VRAM | 16 ГБ | 40/80 ГБ |

**Важно про 5070 Ti.** Blackwell требует сборок PyTorch не ниже CUDA 12.8. Образ
на cu121 или cu124 запустится, отработает инициализацию и упадёт на первом
forward с `no kernel image is available for execution on the device`. Ошибка
выглядит как поломка драйвера, хотя это несовпадение архитектуры. Поэтому в
`Dockerfile` индекс torch зафиксирован на `cu128` — на A100 та же сборка
работает штатно.

Потребление VRAM: layout (RT-DETR) и TableFormer у docling укладываются в
3–4 ГБ, bge-m3 в fp16 добавляет ~1.5 ГБ на экземпляр, а их два. На 16 ГБ
помещается с запасом.

### Софт

Docker с nvidia-container-toolkit. Для запуска с хоста — Python 3.11+:

```bash
# torch ПЕРВЫМ и явно, иначе FlagEmbedding подтянет сборку с дефолтного PyPI
pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt -r requirements-embed.txt
```

## Быстрый старт (dev)

Один раз на хосте — каталог под веса, который переживает пересборку контейнеров:

```bash
mkdir -p /home/dodo/storage/docling-models
sudo chown -R 1001:0 /home/dodo/storage/docling-models
sudo chmod -R g+rwX /home/dodo/storage/docling-models
```

UID 1001 — тот же, под которым работают и `docling-serve`, и наши образы: том с
весами шарится без возни с правами.

```bash
cp ingest.env.example ingest.env
docker compose -f docker-compose.dev.yml up -d --build
docker compose -f docker-compose.dev.yml exec api alembic upgrade head
```

Первый запуск долгий: `docling-models-init` скачивает layout, tableformer,
easyocr, rapidocr и **веса bge-m3 целиком** (~5 ГБ), после чего завершается.
`docling` и `api` стартуют только после его успешного выхода.

Миграции автоматически не применяются — отдельного init-контейнера нет
намеренно: при одной реплике `api` хватает `exec`, а при двух гонку двух
`upgrade head` надо разруливать явно.

Проверка:

```bash
curl -s localhost:8011/health | jq
# {"status":"ok","docling":true,"opensearch":true,"postgres":true,
#  "redis":true,"storage":true,"model":"BAAI/bge-m3"}
```

Dashboards на <http://localhost:5601>, UI docling на
<http://localhost:5001/ui> — туда можно закинуть проблемный PDF руками и
посмотреть, что вернули layout и OCR, не гоняя пайплайн целиком.

### Без Docker

```bash
python -m app.main                                   # api
rq worker -u redis://localhost:6379/1 ingest maintenance   # worker
```

`python -m app.main` поднимает uvicorn с параметрами из `Settings`. Параметр
`workers` намеренно не выставляется: каждый процесс поднял бы свою пару bge-m3,
то есть N×3 ГБ VRAM и N независимых семафоров к одной карте.

Локальный прогон корпуса мимо HTTP — `python -m scripts.ingest_corpus`.

## Продакшен

```bash
cp ingest.env.example .env   # плюс DOCLING_KEY, OPENSEARCH_PASSWORD,
                             # POSTGRES_PASSWORD, S3_*, INGEST_IMAGE_*
cp deploy/seaweedfs-s3.prod.json.example deploy/seaweedfs-s3.prod.json
docker compose -f docker-compose.prod.yml up -d
```

Образы `api` и `worker` собираются в CI из одного Dockerfile двумя целями и
приезжают из реестра. Пинить по digest, а не по тегу: тег можно молча
перезаписать.

```bash
docker build --target api    -t registry.internal/rag-ingest-api:$TAG .
docker build --target worker -t registry.internal/rag-ingest-worker:$TAG .
```

### Отличия от дева

| | dev | prod |
|---|---|---|
| Исходники | том `./app:ro` под `INGEST_RELOAD` | только из образа |
| Веса | том с весами docling | том `models`, `HF_HUB_OFFLINE=1` |
| SeaweedFS | порты на localhost | наружу не публикуется вовсе |
| OpenSearch | без TLS | TLS + пароль |
| Реплики | по одной | `api` 1, `worker` 2 |

`HF_HUB_OFFLINE` в образе не выставляется: в деве том может быть ещё пуст, и
офлайн-режим превратил бы первый старт в невнятную ошибку про недоступный
репозиторий. В проде включается, когда том гарантированно полон.

### Redis один, очередей две

`docling-serve` в проде использует Redis под свою очередь конверсии на базе `0`
(`DOCLING_SERVE_ENG_RQ_REDIS_URL`), control plane — на базе `1`
(`INGEST_REDIS_URL`). Общий инстанс, раздельные пространства ключей; свести их
на одну базу нельзя.

`--appendonly yes` в обоих окружениях: без него задачи последней минуты
теряются при рестарте молча, а документы навсегда остаются в `pending`.

**API docling без единого воркера принимает задачи, но никто их не выполняет** —
снаружи это выглядит как вечный `pending`. То же верно и для наших воркеров.

### Сколько воркеров

`api` — ровно одна реплика: он владеет картой и сериализует доступ к ней.
Масштабируется `worker`, у него состояние только в Postgres и Redis.
`replicas: 2` в файле — стартовая догадка. Померь на своём корпусе: если
документы преимущественно текстовые PDF без OCR, узкое место окажется на CPU
docling, а не на нашей стороне.

## Конфигурация

### Сервис (`app/config.py`)

Префикс `INGEST_`, файл `ingest.env`. Полный список — в `ingest.env.example`.

В docker-compose адреса — имена сервисов, а не `localhost`: воркер живёт в
отдельном контейнере и до `localhost` родителя не достучится.

### OCR и русский язык

Рабочий движок — **EasyOCR** с языками `ru,en`.

`rapidocr` при этом всё равно должен быть скачан в `docling-models-init`:
docling-serve на старте прогревает пайплайн с дефолтными опциями, а дефолтный
движок — `auto`, который выбирает RapidOCR. Без этих весов контейнер падает с
`FileNotFoundError` ещё до первого запроса.

Русскую модель EasyOCR приходится тянуть отдельным вызовом `easyocr.Reader`:
при заданном `artifacts_path` docling считает режим офлайновым и отключает
докачку весов в рантайме, а `docling-tools` кладёт только детектор и латиницу.

Если PDF заведомо текстовые, `do_ocr=false` экономит львиную долю времени.

## HTTP API

Всё под `/v1/platform` проксируется мастером через catch-all и скоупится по
`X-User-Id`. Обращение к чужому набору → `404`, а не `403`: существование чужого
ресурса — тоже информация.

### Наборы

```
POST   /v1/platform/rags                        создать
GET    /v1/platform/rags                        список своих
GET    /v1/platform/rags/{id}
PATCH  /v1/platform/rags/{id}                   частичное обновление
DELETE /v1/platform/rags/{id}                   soft-delete + фоновая уборка
PUT    /v1/platform/rags/{id}/icon              multipart
GET    /v1/platform/rags/{id}/icon
```

```bash
U=11111111-1111-1111-1111-111111111111

curl -X POST localhost:8011/v1/platform/rags \
  -H "Content-Type: application/json" -H "X-User-Id: $U" \
  -d '{"name": "Регламенты", "top_k": 5, "score_threshold": 0.4}'
```

```json
{"id": "6f3c...", "name": "Регламенты", "description": null,
 "status": "empty", "has_icon": false,
 "documents": {"total": 0, "ready": 0, "failed": 0, "pending": 0},
 "chunks_total": 0, "has_pending": false,
 "config": {"prompt": null, "temperature": 0.3, "top_k": 5,
            "score_threshold": 0.4},
 "created_at": "...", "updated_at": "..."}
```

`PATCH` использует `exclude_unset`: не переданные поля сохраняют текущие
значения, а не затираются в `null`.

### Документы

```
POST   /v1/platform/rags/{id}/documents              multipart, N файлов -> 202
GET    /v1/platform/rags/{id}/documents
DELETE /v1/platform/rags/{id}/documents/{doc_id}
POST   /v1/platform/rags/{id}/imports/archive        multipart zip -> 202
GET    /v1/platform/rags/{id}/imports/{batch_id}
```

```bash
curl -X POST localhost:8011/v1/platform/rags/$RAG/documents \
  -H "X-User-Id: $U" -F "files=@a.pdf" -F "files=@b.docx"
```

```json
{"documents": [
  {"id": "1a2b...", "filename": "a.pdf", "status": "pending", "duplicate_of": null},
  {"id": "9f8e...", "filename": "b.docx", "status": "success", "duplicate_of": "9f8e..."}
]}
```

`duplicate_of` заполнен, если такой контент в наборе уже есть: возвращается
существующий документ, новый не создаётся.

### Внутренняя ручка для agentic_rag

```
GET  /v1/internal/rags/{id}?user_id=<uuid>
POST /v1/internal/documents/lookup?user_id=<uuid>
```

Отдаёт конфиг набора и заодно проверяет владение — `404`, если набор чужой или
удалён. Это и есть механизм изоляции: отдельного нет.

Кэша нет намеренно. Один дешёвый вызов на фоне 4–6 обращений к LLM стоит доли
процента времени хода, зато правка конфига применяется со следующего сообщения,
а удаление набора мгновенно закрывает доступ во всех уже открытых вкладках.

`POST /documents/lookup` — batch-подстановка имён по списку
`document_ids` (до 100 за раз). `agentic_rag` зовёт её при финализации
хода и кладёт результат в `message_sources.filename` снимком: иначе после
удаления документа подписи под цитатами в старых ответах потеряются.

Всегда `200`, даже если не нашлось ничего. Отсутствующие документы просто
не попадают в ответ — документ мог быть удалён между генерацией ответа и
подстановкой имён, и это штатный ход событий, а не ошибка запроса. Порядок
не гарантирован: клиент строит словарь по `document_id`.

Эти ручки через мастер не проксируются — закрывать их должна сеть, а не
маршрутизация.

### Операторские

```
POST /admin/rags/{id}/imports/s3     {"prefix": "..."}
GET  /admin/staging?prefix=
```

Путь намеренно **не** начинается с `v1/`: catch-all мастера форвардит любой путь
под `v1/` без разбора, так что `/v1/admin/...` уехал бы наружу автоматически.

### `POST /embed`

```bash
curl -X POST localhost:8011/embed \
  -H "Content-Type: application/json" \
  -d '{"texts": ["порядок расторжения договора"], "pool": "query"}'
```

```json
{"model": "BAAI/bge-m3",
 "embeddings": [{"dense": [/* 1024 */], "sparse": {"12345": 0.21}}]}
```

Этот эндпоинт решает главную проблему отказа от ML Commons. Когда вектор запроса
считает клиент, ничто не мешает ему однажды посчитать его чуть иначе: другая
версия модели, другой пулинг, забытая нормализация. Ошибка не выдаст
исключения — она просто просадит выдачу, и причину будешь искать в настройках
HNSW. Один эндпоинт на всю систему делает такое расхождение невозможным.

`texts` — список, и это существенно: все варианты multi-query должны уходить
**одним** вызовом, иначе получится N сетевых round-trip'ов, каждый за семафором
GPU.

`pool` выбирает экземпляр модели: `query` (по умолчанию) — чат, `ingest` —
воркеры индексации.

**Префиксы не нужны.** bge-m3 обучалась без инструкций — никаких `query:` и
`passage:`, в отличие от e5. Забытый от e5 префикс не даст ошибки, он тихо
просадит качество на несколько пунктов NDCG.

### `GET /health`

Проверяет docling, OpenSearch, Postgres, Redis и объектное хранилище.
`degraded`, если что-то недоступно.

## Схема Postgres

```sql
rag_sets
  id, owner_id, name, description
  prompt, temperature, top_k, score_threshold     -- конфиг, весь query-time
  icon_key                                        -- ключ в SeaweedFS, не байты
  created_at, updated_at, deleted_at
  -- unique (owner_id, lower(name)) where deleted_at is null

documents
  id, rag_id, filename, size_bytes, content_hash
  storage_key                                     -- ключ в SeaweedFS
  origin (upload|archive|s3), origin_ref
  status (pending|processing|success|failed), error, chunks_count
  -- unique (rag_id, content_hash)

import_batches
  id, rag_id, kind (archive|s3), status
  documents_total, documents_created, documents_skipped, error

ingest_jobs
  id, document_id, rq_job_id, attempts
  started_at, finished_at, error
```

**Байты файлов в Postgres не хранятся** — ни одного `bytea`. Связь с SeaweedFS
только через `storage_key` и `icon_key`.

`unique (rag_id, content_hash)` даёт дедупликацию: повторная загрузка того же
файла возвращает существующий документ. Для архивов и импорта это основной
путь — они почти гарантированно пересекутся по содержимому. Одинаковый файл в
двух разных наборах — два независимых документа, это корректно.

### Миграции

Пишутся автогенерацией, руками — никогда:

```bash
alembic revision --autogenerate -m "описание"
alembic upgrade head
```

`sqlalchemy.url` в `alembic.ini` пустой намеренно: он берётся из
`INGEST_DATABASE_URL` в `alembic/env.py`. Два источника правды о строке
подключения рано или поздно разъезжаются, и миграция уезжает не в ту базу.

### Статус набора — производная

Не хранимое поле, а агрегат по документам на чтение:

```
documents_total == 0                    -> empty
есть хоть один success                  -> ready      (даже если часть в работе)
нет success, есть pending/processing    -> ingesting
нет success, все failed                 -> failed
```

`ready` при частичной готовности — сознательно: чат уже осмыслен на том, что
проиндексировано. Прогресс UI берёт из счётчиков, `has_pending` подсказывает,
что список ещё пополняется.

Машины состояний нет, потому что конфиг целиком query-time и переиндексации не
бывает — она бы выродилась в одно состояние.

## Жизненный цикл документа

**Загрузка: объект → строка → задача.** Порядок фиксирован.

Упали после записи объекта — остался осиротевший объект без строки: невидим, не
мешает, подчищается фоновой сверкой по префиксу. Обратный порядок был бы хуже:
воркер получил бы задачу на несуществующий файл, и документ навсегда завис бы в
`failed` — а это видно пользователю.

**Удаление: строка → объект.** Наоборот, чтобы пользователь мгновенно перестал
видеть документ, а уборка ушла в фон.

**Обработка воркером:**

```
status=processing
  -> presigned GET на объект в SeaweedFS
  -> http_sources в docling-serve (байты не идут через наш процесс дважды)
  -> чанки
  -> POST /embed с pool="ingest"
  -> bulk в OpenSearch
status=success, chunks_count
```

Общей транзакции у Postgres и SeaweedFS нет, отсюда и фиксированный порядок:
это единственный доступный способ сделать рассинхрон безвредным.

## Конфиг набора

```
name, description, prompt, temperature, top_k, score_threshold
```

Ни одно поле не влияет на индексацию, поэтому **переиндексация как операция не
нужна вообще**: любая правка применяется со следующего сообщения.

Границы применения:

- `prompt` **дополняет** системный промпт агента отдельным блоком, не заменяет
  его. Иначе пользователь одной формулировкой сносит требования к цитированию и
  к структурированному выводу, и генерация начинает отдавать невалидный JSON.
- `temperature` применяется **только к финальному ответу**. У rewriter и eval
  она захардкожена в `0.0` — это детерминированные шаги планировщика, и
  пользователь, выкрутивший температуру, не должен ломать себе разбор запроса.
- Промпты rewriter / multi-query / eval пользователю недоступны: они
  платформенные и не про предметную область.

Валидация: `temperature` 0…1, `top_k` 1…10, `score_threshold` 0…1, `prompt` до
4000 символов. Проверяется и pydantic-схемой, и `CHECK`-ограничением в БД.

Потолок `top_k` — не вкусовщина: пул растёт как
`top_k × 3 ветки × N вариантов multi-query × итерации`, и он же ограничивает
размер контекста, уходящего в eval агентного цикла.

## Загрузка архивом и импорт

Три точки входа сходятся в одну таблицу `documents` и один воркер:

| Ручка | Источник | Кто |
|---|---|---|
| `.../documents` | multipart, N файлов | пользователь |
| `.../imports/archive` | один zip | пользователь |
| `/admin/rags/{id}/imports/s3` | префикс в staging | оператор |

Архив и импорт разворачиваются задачей в очереди, порождающей задачи-потомки:
батч из трёхсот файлов — это один индикатор в UI (`import_batches`), а не
триста строк. Разбор в самой ручке означал бы удержание запроса на всё время
распаковки.

### Лимиты архива — серверные

```
INGEST_ARCHIVE_MAX_ENTRIES          2000
INGEST_ARCHIVE_MAX_UNCOMPRESSED     5 ГБ
INGEST_ARCHIVE_MAX_RATIO            120      коэффициент сжатия на запись
INGEST_ARCHIVE_MAX_FILE_SIZE        200 МБ
```

Ни один из этих лимитов не про качество поиска — все про то, что архив приходит
от пользователя, и задавать их он не должен.

Первые три проверяются **до распаковки**, по центральному каталогу zip;
нарушение любого отклоняет архив целиком. Это защита от zip-бомбы, частичная
обработка тут бессмысленна: к моменту проверки постфактум бомба уже
развернулась.

Дополнительно:

- **имена записей санитизируются.** Даже если мы не пишем на диск, имя записи
  становится `filename` и уезжает в `storage_key`, так что `../../etc/passwd`
  сплющивается до `passwd`. Коллизии после сплющивания (`a/doc.pdf` и
  `b/doc.pdf`) разводятся суффиксом;
- **вложенные архивы отклоняются**, рекурсивно не разворачиваются: глубина
  рекурсии — ещё один вектор бомбы;
- **зашифрованный архив** — падение с внятной ошибкой, а не разворачивание в
  мусор;
- **неподдерживаемое расширение внутри** — пропуск записи со статусом, батч
  продолжается. Это единственное, что не отклоняет архив целиком.

Формат — только zip: у tar нет центрального каталога, размеры до распаковки не
видны, и защита от бомбы строится иначе.

### Импорт из staging

Пользователь в staging не ходит: доступы туда есть только у оператора, ручка под
`/admin`. Пользовательский импорт требует выдачи скоупленных по префиксу
доступов и отложен.

Импорт **копирует** объект в `rag-docs` через server-side copy, а не ссылается
на staging. Иначе уборка staging выбила бы документы из-под набора, а
переиндексация через полгода упёрлась бы в удалённый объект. После копирования
все три источника документов неразличимы.

## Объектное хранилище

SeaweedFS через S3-совместимый шлюз. Выбран вместо Garage по лицензии: Apache
2.0 против AGPL — тот же критерий юридической чистоты, по которому OpenSearch
выбран вместо Elasticsearch.

| Бакет | Ключ |
|---|---|
| `rag-docs` | `{rag_id}/{document_id}/{filename}` |
| `rag-icons` | `{rag_id}` |
| `rag-staging` | `archives/{rag_id}/{batch_id}.zip`, операторские префиксы |

Три операции несут архитектурный смысл:

- **presigned GET** — docling качает файл сам через `http_sources`, и байты не
  проходят через наш процесс второй раз;
- **server-side copy** — импорт из staging не гонит содержимое через нас;
- **потоковая запись** — файл не поднимается в память процесса целиком.

Одна нода поднимает master, volume, filer и S3-шлюз одним процессом
(`weed server -filer -s3`). Разносить роли имеет смысл, когда упрёмся в объём
или IO.

`-s3.config` обязателен: без файла identity шлюз пускает анонимно. Дев-конфиг
лежит в `deploy/seaweedfs-s3.json` с ключами `rag/rag`, прод-файл копируется из
`.example` и в git не коммитится. Права `Admin` нужны только под создание
бакетов на первом старте; после этого их можно снять.

### Иконки

Whitelist `image/png`, `image/jpeg`, `image/webp`; лимит 512 КБ; переупаковка
на сервере в PNG фиксированного размера.

**SVG не принимаем** — иконка отдаётся с того же origin, что и фронт, а SVG
является исполняемым документом. Переупаковка остальных форматов обязательна по
той же причине: она отбрасывает всё, что не является пикселями — метаданные,
довесок после конца изображения, полиглот-файлы.

## Структура индекса

```
rag_id          keyword       набор-владелец; обязателен
document_id     keyword       UUID документа
chunk_index     integer       порядковый номер чанка
content         text/ru_en    BM25 с русской морфологией
headings        text/ru_en    цепочка родительских заголовков
pages           integer[]     страницы исходника — для цитирования
content_hash    keyword       хэш содержимого, для skip_unchanged
content_vector  knn_vector    1024 dim, HNSW/faiss, cosinesimil
content_sparse  rank_features lexical_weights из bge-m3
```

`headings` — именно `text`, а не `keyword`: как `keyword` поле не анализируется,
и BM25 по заголовкам сводится к точному совпадению всей цепочки целиком.

### Почему 1024, а не 384

Переход с multilingual-e5-small на bge-m3 меняет размерность втрое, и HNSW-граф
растёт соответственно. Отсюда правки в compose:

- heap 512m → 2g в деве, 16g в проде;
- `knn.memory.circuit_breaker.limit` — HNSW-графы лежат **вне** heap, и этот
  лимит с `-Xmx` не связан.

С 384 измерениями 512m ещё как-то жило. С 1024 и bulk пачками по несколько сотен
документов упрётесь в потолок быстро и получите circuit breaker посреди загрузки.

Прод-heap считается как половина RAM ноды, но не выше ~31 ГБ: за этой границей
JVM теряет сжатые указатели, и heap начинает работать хуже, а не лучше.

## Мультитенантность

Индекс **один на всю платформу**. Наборы разделяются полем `rag_id`, и это
граница безопасности, а не оптимизация: забытый фильтр — не деградация выдачи, а
утечка чужих документов в чужой ответ, причём тихая.

Поэтому:

- фильтр `rag_id` обязателен во **всех трёх** ветках поиска — BM25, kNN и
  `rank_features`. Последняя забывается чаще всего;
- в kNN фильтр ставится **внутрь** ветки, а не post-filter снаружи;
- ветки собираются фабрикой с `rag_id` обязательным аргументом, чтобы написать
  ветку без фильтра было невозможно, а не «не забыть».

Индекс-на-набор рассматривался и отвергнут: модель эмбеддингов фиксирована,
чанкинг общий, конфиг весь query-time — значит маппинг у всех наборов
идентичен, и разделение дало бы только шардовый оверхед. Тысяча наборов — это
тысяча шардов и захлебнувшаяся мастер-нода при нулевом выигрыше в качестве.

### Про идемпотентность

`_id` чанка строится детерминированно:

```
blake2b(f"{rag_id}:{document_id}:{chunk_index}")
```

Операция — `index`, а не `create`, поэтому повторный прогон перезаписывает
документы, а не падает на конфликте и не плодит дубли.

Ключ намеренно не зависит от имени файла или пути. Прежняя формула
`blake2b(source_uri:chunk_index)` в общем индексе коллизионна: `report.pdf` у
двух пользователей давал один `_id`, и второй молча перезаписывал чанки первого,
без ошибки и без конфликта. `document_id` — UUID, коллизия невозможна по
построению.

`skip_unchanged` сравнивает `content_hash` в границах документа. Оговорка: если
документ поправили в середине, все последующие чанки сдвинутся по индексу и
переиндексируются целиком. Это корректно, но не оптимально.

### Удаление

`delete_rag(rag_id)` и `delete_document(rag_id, document_id)` —
`delete_by_query` с `conflicts=proceed`, вызываются из фоновых задач уборки
после того, как строка в Postgres уже удалена.

## Шкала скоров и score_threshold

`_score` от kNN — **не косинус**, а монотонное преобразование расстояния. Для
faiss/`cosinesimil` OpenSearch отдаёт `1 / (1 + cosineDistance)`, где
`cosineDistance = 1 - cos`. Формула отличается между движками и версиями.

`app/search/scoring.py` даёт пару `score_from_cosine` / `cosine_from_score`:
порог задаётся в терминах косинуса (понятная пользователю величина), а в запрос
уходит пересчитанный `min_score`.

Формула не берётся на веру. `verify_cosine_calibration()` вызывается на старте:
берёт чанк из индекса, ищет его же по собственному вектору и проверяет, что
обратное преобразование даёт ≈ 1.0. Расхождение роняет сервис. Без этой проверки
ошибка не даёт исключения — она тихо смещает порог, и пользователь получает не
то, что задал. Пустой индекс проверку пропускает.

Порог применяется **только к kNN-ветке и до фьюжна**: RRF-score ранговый, между
итерациями несравним и абсолютного смысла не имеет. BM25 и `rank_features`
режутся по `top_k`.

## Поиск

Три ветки, объединяемые на стороне OpenSearch. Векторы запроса берутся из
`/embed`. Сам поиск выполняет `agentic_rag`, здесь он приведён потому, что
структуру индекса задаёт этот сервис.

```json
{
  "query": {
    "hybrid": {
      "queries": [
        { "bool": {
            "must": [{ "match": { "content": { "query": "<текст>" } } }],
            "filter": [{ "term": { "rag_id": "<uuid>" } }]
        }},
        { "knn": {
            "content_vector": {
              "vector": [/* dense из /embed */],
              "k": 100,
              "filter": { "term": { "rag_id": "<uuid>" } }
            }
        }},
        { "bool": {
            "should": [{ "rank_feature": { "field": "content_sparse.12345", "boost": 0.7 } }],
            "filter": [{ "term": { "rag_id": "<uuid>" } }]
        }}
      ]
    }
  }
}
```

Два момента, на которых легко ошибиться:

**Фильтр должен быть внутри `knn`**, а не post-filter снаружи. Иначе HNSW сначала
наберёт k соседей по всему индексу, а фильтр отрежет от них большую часть, и
выдача окажется короче ожидаемой.

**`pagination_depth` в конфиге search-пайплайна** должен быть достаточно большим,
чтобы до слияния дошло нужное число кандидатов от каждой ветки. Слишком малое
значение обрежет ветки до слияния, и RRF будет работать с обеднённым материалом.

Слияние настраивается через `score-ranker-processor` (RRF, OpenSearch 2.19+) или
`normalization-processor`. Качество меряется через `_rank_eval` по NDCG@10.

## Диагностика

**`no kernel image is available for execution on the device`**
Сборка torch старше CUDA 12.8, а карта — Blackwell. Проверь `TORCH_INDEX_URL` в
сборке образа `api` и тег образа docling.

**Контейнер docling падает с `FileNotFoundError` до первого запроса**
Не скачаны веса RapidOCR. Даже при работе на EasyOCR они нужны для прогрева
пайплайна с дефолтными опциями. Проверь, что `docling-models-init` отработал.

**Сервис не стартует: «Калибровка косинуса не сошлась»**
Преобразование `_score` не соответствует движку или версии OpenSearch. Проверь
`space_type` и `engine` в маппинге и поправь `app/search/scoring.py`. Падение
намеренное: молча работающий, но смещённый порог хуже отказа старта.

**Документы вечно в `pending`**
Воркеры не подняты, либо `INGEST_REDIS_URL` не совпадает у `api` и `worker`,
либо очереди названы по-разному. Проверь `docker compose ps` и
`rq info -u $INGEST_REDIS_URL`.

**Воркер падает на `/embed` с `Connection refused`**
`INGEST_SELF_URL` указывает на `localhost`, а воркер живёт в отдельном
контейнере, либо указывает на платформенный порт вместо внутреннего.
В compose должно быть `http://api:8012`.

**Чат тормозит во время заливки корпуса**
Оба сценария делят один экземпляр модели. Включи
`INGEST_SEPARATE_QUERY_EMBEDDER=true`.

**`404` на своём же наборе из agentic_rag**
`user_id` в `/v1/internal/rags/{id}` не совпадает с `owner_id`. Скорее всего
мастер не пробросил `X-User-Id` или агент подставил не то значение.

**Архив отклонён целиком, а файлов в нём немного**
Сработал лимит по коэффициенту сжатия: текстовые файлы с длинными повторами
сжимаются в сотни раз и выглядят как бомба. Подними
`INGEST_ARCHIVE_MAX_RATIO`, если корпус действительно такой.

**Чанки без заголовков в начале**
Клиент забрал не то поле ответа. `_extract_texts` в `app/docling/client.py`
перебирает `contextualized_text` → `text` → `raw_text`, потому что имя поля
различается между версиями. Полная схема всегда на `/docs` живого сервера — она
авторитетнее любой документации, включая эту.

**Границы чанков не совпадают с ожиданиями**
Не передан `chunking_tokenizer`, и HybridChunker считает токены дефолтным
токенизатором. Он должен совпадать с эмбеддером — отсюда
`ChunkingOptions(tokenizer="BAAI/bge-m3")`.

**Circuit breaker при bulk-загрузке**
Мало heap или исчерпан off-heap под HNSW. Подними `-Xmx` и проверь
`knn.memory.circuit_breaker.limit`.

**Изображения не приходят из чанк-эндпоинта**
Известное ограничение: ссылки на ассеты не возвращаются даже при
`include_images=true`. Если нужны картинки — отдельный вызов `/v1/convert/*` с
`image_export_mode=referenced`.
