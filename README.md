# RAG Ingest: docling → bge-m3 → OpenSearch

Конвейер подготовки базы знаний. Документы любых форматов превращаются в чанки
с сохранённой структурой и провенансом, векторизуются и попадают в OpenSearch,
готовые к гибридному поиску.

Сервис мультитенантный: чанки разных наборов лежат в одном индексе и
разделяются полем `rag_id`. Идентичность документа задаёт вызывающая сторона —
см. [Мультитенантность](#мультитенантность).

## Архитектура

```
             ┌──────────────┐
   файл ───► │  app.main    │  FastAPI: приём файлов, /embed
             └──────┬───────┘
                    │
        ┌───────────┴────────────┐
        ▼                        ▼
┌───────────────┐        ┌───────────────┐
│ docling-serve │        │    bge-m3     │
│ parse+chunk   │        │ dense+sparse  │
│    (GPU)      │        │ ingest+query  │
└───────┬───────┘        └───────┬───────┘
        │      чанки             │  векторы
        └───────────┬────────────┘
                    ▼
            ┌───────────────┐
            │  OpenSearch   │
            │ BM25 + kNN +  │
            │ rank_features │
            └───────────────┘
```

### Роли компонентов

**docling-serve** закрывает стадии Parse, Structure и Chunk. На выходе —
`DoclingDocument`: дерево с заголовками, таблицами и списками, где у каждого
элемента есть провенанс (номер страницы, bbox). Дальше HybridChunker режет это
дерево с учётом токенизатора эмбеддера: не разрывает таблицы, склеивает мелкие
соседние блоки, добавляет к каждому чанку родительские заголовки.

**bge-m3** считает из одного прохода плотный вектор (1024 измерения) и
разреженные лексические веса. Второй выход — готовая замена SPLADE для третьей
ветки гибридного поиска, без отдельной модели.

Модель поднимается **двумя экземплярами**: один обслуживает индексацию, второй —
`/embed`. Подробнее в [Два экземпляра модели](#два-экземпляра-модели).

**OpenSearch** хранит три представления каждого чанка: текст под BM25 с русской
морфологией, плотный вектор в HNSW и разреженные веса в `rank_features`.

## Требования

### GPU

Обе целевые карты покрываются одним образом `docling-serve-cu128`, поэтому дев и
прод работают на одном билде.

| | Dev | Prod |
|---|---|---|
| Карта | RTX 5070 Ti | A100 |
| Архитектура | Blackwell, `sm_120` | Ampere, `sm_80` |
| Минимум CUDA | 12.8 | 11.0 |
| VRAM | 16 ГБ | 40/80 ГБ |

**Важно про 5070 Ti.** Blackwell требует сборок PyTorch не ниже CUDA 12.8. Образ
на cu121 или cu124 запустится, отработает инициализацию и упадёт на первом
forward с `no kernel image is available for execution on the device`. Ошибка
выглядит как поломка драйвера, хотя это несовпадение архитектуры.

Потребление VRAM стандартным пайплайном docling скромное — layout (RT-DETR) плюс
TableFormer укладываются в 3–4 ГБ. bge-m3 в fp16 добавляет около 1.5 ГБ на
экземпляр, а их два. На 16 ГБ помещается с запасом, на A100 остаётся место под
несколько воркеров.

### Софт

- Docker с nvidia-container-toolkit
- Python 3.11+ для загрузчика

```bash
# torch ставится ПЕРВЫМ и явно: FlagEmbedding иначе подтянет сборку
# с дефолтного индекса PyPI, а Blackwell требует CUDA >= 12.8
pip install torch --index-url https://download.pytorch.org/whl/cu128
pip install -r requirements.txt
```

## Быстрый старт (dev)

Перед первым запуском один раз на хосте — каталог под веса, который переживает
пересборку контейнеров:

```bash
mkdir -p /home/dodo/storage/docling-models
sudo chown -R 1001:0 /home/dodo/storage/docling-models
sudo chmod -R g+rwX /home/dodo/storage/docling-models
```

```bash
docker compose -f docker-compose.dev.yml up -d
```

Первый запуск долгий: сервис `docling-models-init` скачивает layout, tableformer,
easyocr, rapidocr и токенизатор bge-m3 (~2–3 ГБ), после чего завершается.
`docling` стартует только после его успешного выхода.

Проверка:

```bash
curl -s localhost:9200/_cluster/health | jq .status
curl -s localhost:5001/health
```

Дев-инстанс docling поднят с UI на <http://localhost:5001/ui> — туда можно
закинуть проблемный PDF руками и посмотреть, что вернули layout и OCR, не гоняя
пайплайн целиком. Dashboards на <http://localhost:5601>.

Загрузка корпуса напрямую, без HTTP-слоя:

```bash
python -m scripts.ingest_corpus
```

Или через API:

```bash
uvicorn app.main:app --port 8000
```

## Продакшен

```bash
cp .env.example .env   # DOCLING_KEY, OPENSEARCH_PASSWORD, DOCLING_IMAGE
docker compose -f docker-compose.prod.yml up -d
```

### Отличия от дева

Образ не собирается, а приезжает из реестра — в `docker-compose.prod.yml` нет
секции `build`. Пинить лучше по digest, а не по тегу: тег можно молча
перезаписать, digest нельзя.

```yaml
image: registry.internal/docling-serve@sha256:abc123...
```

Конверсия уходит в очередь: API ставит задачи в Redis, а работу выполняют
процессы `docling-serve rq-worker`. `DOCLING_SERVE_ENG_RQ_REDIS_URL` обязан
совпадать во всех процессах. **API без единого воркера принимает задачи, но
никто их не выполняет** — снаружи это выглядит как вечный `pending`.

`HF_HUB_OFFLINE=1` гарантирует, что в рантайме ничего не полезет в сеть. Все
веса уже в образе.

### Стоит ли держать OpenSearch тут же

В `docker-compose.prod.yml` он включён, потому что файл задумывался
самодостаточным. Но `single-node` без реплик означает, что потеря диска равна
потере индекса, а поиск и парсинг конкурируют за память и IO совершенно
по-разному. Если кластер уже живёт отдельно — выбрось сервис `opensearch` и
оставь docling с Redis.

### Сколько воркеров

Три реплики в файле — стартовая догадка, не рекомендация. Померь на своём
корпусе: если документы преимущественно текстовые PDF без OCR, узкое место
окажется на CPU, и упрёшься ты в `DOCLING_NUM_THREADS`, а не в карту. Тогда
выгоднее меньше реплик с большим числом потоков каждая.

### Два экземпляра модели

`INGEST_SEPARATE_QUERY_EMBEDDER=true` поднимает вторую копию bge-m3 со своим
семафором. Веса и версия те же, поэтому вектор запроса по-прежнему физически не
может разойтись с вектором документа — ради этого `/embed` и существует.

Причина разделения в другом: заливка корпуса — это сотни батчей подряд. На общем
семафоре запрос из чата ждёт не свои 30 мс, а глубину очереди, умноженную на
время батча, и так на каждой итерации агентного цикла. Второй инстанс стоит
~1.5 ГБ VRAM; если её жалко, флаг выключается и оба сценария делят один
экземпляр.

Отдельно: семафор индексации охватывает **только вызов модели**, а не весь
пайплайн. Если взять его вокруг всей обработки файла, он будет удерживаться всё
время конверсии в docling — минуты на скан, — и `/embed` встанет в очередь за
парсингом PDF.

### OCR и русский язык

Рабочий движок — **EasyOCR** с языками `ru,en`.

`rapidocr` при этом всё равно должен быть скачан в `docling-models-init`:
docling-serve на старте прогревает пайплайн с дефолтными опциями, а дефолтный
движок — `auto`, который выбирает RapidOCR. Без этих весов контейнер падает с
`FileNotFoundError` ещё до первого запроса.

Русскую модель EasyOCR приходится тянуть отдельным вызовом `easyocr.Reader`:
при заданном `artifacts_path` docling считает режим офлайновым и отключает
докачку весов в рантайме, а `docling-tools` кладёт только детектор и латиницу.

Если PDF заведомо текстовые, `do_ocr=false` экономит львиную долю времени.

## HTTP API

### `POST /ingest/file`

Multipart-загрузка. Отвечает `202` сразу — конверсия PDF занимает секунды на
страницу, держать соединение открытым незачем.

`rag_id` и `document_id` обязательны и должны быть UUID: от них строится `_id`
чанка. Пока их передаёт вызывающая сторона; когда появится control plane, эта
ручка уедет под `/v1/platform/rags/{id}/documents`, и идентификаторы начнёт
выдавать он.

```bash
curl -X POST localhost:8000/ingest/file \
  -H "X-Api-Key: $KEY" \
  -F "file=@report.pdf" \
  -F "rag_id=6f3c0f6e-0000-4000-8000-000000000001" \
  -F "document_id=1a2b3c4d-0000-4000-8000-000000000002"
```

```json
{"job_id": "a3f...", "filename": "report.pdf",
 "rag_id": "6f3c...", "document_id": "1a2b...",
 "status": "pending", "chunks_loaded": 0}
```

### `GET /ingest/status/{job_id}`

```json
{"job_id": "a3f...", "status": "success", "chunks_loaded": 47, "error": null}
```

Реестр задач живёт в памяти процесса и не переживает рестарт. Это временное
решение: его место займут таблица `ingest_jobs` в Postgres и очередь Redis RQ.

### `POST /embed`

Векторизация той же моделью, что обрабатывала документы.

```bash
curl -X POST localhost:8000/embed \
  -H "Content-Type: application/json" \
  -d '{"texts": ["порядок расторжения договора"]}'
```

```json
{"model": "BAAI/bge-m3",
 "embeddings": [{"dense": [/* 1024 */], "sparse": {"12345": 0.21}}]}
```

Этот эндпоинт решает главную проблему отказа от ML Commons. Когда вектор запроса
считает клиент, ничто не мешает ему однажды посчитать его чуть иначе: другая
версия модели, другой пулинг, забытая нормализация. Ошибка не выдаст
исключения — она просто просадит выдачу, и причину будешь искать в настройках
HNSW. Один эндпоинт на всю систему делает такое расхождение невозможным.

`texts` — список, и это существенно: все варианты multi-query должны уходить
**одним** вызовом, иначе получится N сетевых round-trip'ов, каждый за семафором
GPU.

**Префиксы не нужны.** bge-m3 обучалась без инструкций — никаких `query:` и
`passage:`, в отличие от e5. Забытый от e5 префикс не даст ошибки, он тихо
просадит качество на несколько пунктов NDCG.

### `GET /health`

Проверяет доступность docling и OpenSearch. `degraded`, если что-то из этого
недоступно.

## Структура индекса

```
rag_id          keyword       набор-владелец; обязателен
document_id     keyword       UUID документа
chunk_index     integer       порядковый номер чанка
content         text/ru_en    BM25 с русской морфологией
headings        text/ru_en    цепочка родительских заголовков
pages           integer[]     страницы исходника — для цитирования
content_hash    keyword       хэш содержимого, для skip_unchanged
content_vector  knn_vector    1024 dim, HNSW/faiss, cosinesimil
content_sparse  rank_features lexical_weights из bge-m3
```

`headings` — именно `text`, а не `keyword`: как `keyword` поле не анализируется,
и BM25 по заголовкам сводится к точному совпадению всей цепочки целиком.

### Почему 1024, а не 384

Переход с multilingual-e5-small на bge-m3 меняет размерность втрое, и HNSW-граф
растёт соответственно. Отсюда правки в compose:

- heap 512m → 2g в деве, 16g в проде;
- `knn.memory.circuit_breaker.limit` — HNSW-графы лежат **вне** heap, и этот
  лимит с `-Xmx` не связан.

С 384 измерениями 512m ещё как-то жило. С 1024 и bulk пачками по несколько сотен
документов упрётесь в потолок быстро и получите circuit breaker посреди загрузки.

Прод-heap считается как половина RAM ноды, но не выше ~31 ГБ: за этой границей
JVM теряет сжатые указатели, и heap начинает работать хуже, а не лучше.

## Мультитенантность

Индекс **один на всю платформу**. Наборы разделяются полем `rag_id`, и это
граница безопасности, а не оптимизация: забытый фильтр — не деградация выдачи, а
утечка чужих документов в чужой ответ, причём тихая.

Поэтому:

- фильтр `rag_id` обязателен во **всех трёх** ветках поиска — BM25, kNN и
  `rank_features`. Последняя забывается чаще всего;
- в kNN фильтр ставится **внутрь** ветки, а не post-filter снаружи;
- ветки собираются фабрикой с `rag_id` обязательным аргументом, чтобы написать
  ветку без фильтра было невозможно, а не «не забыть».

### Про идемпотентность

`_id` чанка строится детерминированно:

```
blake2b(f"{rag_id}:{document_id}:{chunk_index}")
```

Операция — `index`, а не `create`, поэтому повторный прогон перезаписывает
документы, а не падает на конфликте и не плодит дубли.

Ключ намеренно не зависит от имени файла или пути. Прежняя формула
`blake2b(source_uri:chunk_index)` в общем индексе коллизионна: `report.pdf` у
двух пользователей давал один `_id`, и второй молча перезаписывал чанки первого,
без ошибки и без конфликта. `document_id` — UUID, коллизия невозможна по
построению.

Побочный эффект: путь к временному файлу при загрузке через HTTP на идентичность
больше не влияет.

`skip_unchanged` дополнительно сравнивает `content_hash` в границах документа и
пропускает неизменившиеся чанки. Оговорка: если документ поправили в середине,
все последующие чанки сдвинутся по индексу и переиндексируются целиком. Это
корректно, но не оптимально. Для больших документов с точечными правками лучше
строить `_id` от хэша заголовков плюс содержимого — тогда сдвиг не каскадирует.

### Удаление

`OpenSearchLoader.delete_rag(rag_id)` и `delete_document(rag_id, document_id)` —
`delete_by_query` с `conflicts=proceed`. Первый вызывается при удалении набора,
второй — при удалении отдельного документа.

## Шкала скоров и score_threshold

`_score` от kNN — **не косинус**, а монотонное преобразование расстояния. Для
faiss/`cosinesimil` OpenSearch отдаёт `1 / (1 + cosineDistance)`, где
`cosineDistance = 1 - cos`. Формула отличается между движками и версиями.

`app/search/scoring.py` даёт пару `score_from_cosine` / `cosine_from_score`:
порог задаётся в терминах косинуса (понятная пользователю величина), а в запрос
уходит пересчитанный `min_score`.

Формула не берётся на веру. `OpenSearchLoader.verify_cosine_calibration()`
вызывается на старте: берёт чанк из индекса, ищет его же по собственному
вектору и проверяет, что обратное преобразование даёт ≈ 1.0. Расхождение роняет
сервис. Без этой проверки ошибка не даёт исключения — она тихо смещает порог, и
пользователь получает не то, что задал. Пустой индекс проверку пропускает.

## Поиск

Три ветки, объединяемые на стороне OpenSearch. Векторы запроса берутся из
`/embed`.

```json
{
  "query": {
    "hybrid": {
      "queries": [
        { "bool": {
            "must": [{ "match": { "content": { "query": "<текст>" } } }],
            "filter": [{ "term": { "rag_id": "<uuid>" } }]
        }},
        { "knn": {
            "content_vector": {
              "vector": [/* dense из /embed */],
              "k": 100,
              "filter": { "term": { "rag_id": "<uuid>" } }
            }
        }},
        { "bool": {
            "should": [{ "rank_feature": { "field": "content_sparse.12345", "boost": 0.7 } }],
            "filter": [{ "term": { "rag_id": "<uuid>" } }]
        }}
      ]
    }
  }
}
```

Два момента, на которых легко ошибиться:

**Фильтр должен быть внутри `knn`**, а не post-filter снаружи. Иначе HNSW сначала
наберёт k соседей по всему индексу, а фильтр отрежет от них большую часть, и
выдача окажется короче ожидаемой.

**`pagination_depth` в конфиге search-пайплайна** должен быть достаточно большим,
чтобы до слияния дошло нужное число кандидатов от каждой ветки. Слишком малое
значение обрежет ветки до слияния, и RRF будет работать с обеднённым материалом.

Слияние настраивается через `score-ranker-processor` (RRF, OpenSearch 2.19+) или
`normalization-processor`. Качество меряется через `_rank_eval` по NDCG@10.

## Как файлы попадают в docling

Только по HTTP. docling-serve — stateless-сервис без файлового входа: он не умеет
смотреть в примонтированную папку и не имеет понятия «путь к документу».
Монтировать в него том с корпусом бессмысленно.

| Способ | Класс клиента | Когда |
|---|---|---|
| multipart | `DoclingFileClient` | Файлы на диске рядом с загрузчиком. Основной путь |
| base64 в `file_sources` | — | Если по дороге прокси, ломающий multipart. +33% к объёму |
| `http_sources` | `DoclingUrlClient` | Файлы в объектном хранилище: presigned URL, сервис качает сам |

Третий вариант экономнее для объектного хранилища — байты не проходят через твой
процесс дважды.

## Диагностика

**`no kernel image is available for execution on the device`**
Образ собран под CUDA старше 12.8, а карта — Blackwell. Проверь тег образа:
нужен `docling-serve-cu128` или `cu130`.

**Контейнер docling падает с `FileNotFoundError` до первого запроса**
Не скачаны веса RapidOCR. Даже при работе на EasyOCR они нужны для прогрева
пайплайна с дефолтными опциями. Проверь, что `docling-models-init` отработал
успешно.

**Задачи вечно в `pending`**
Работают только API-контейнеры, воркеры не поднялись. Проверь
`docker compose ps` и совпадение `DOCLING_SERVE_ENG_RQ_REDIS_URL` во всех
процессах.

**Сервис не стартует: «Калибровка косинуса не сошлась»**
Преобразование `_score` не соответствует движку или версии OpenSearch. Проверь
`space_type` и `engine` в маппинге и поправь `app/search/scoring.py`. Падение
намеренное: молча работающий, но смещённый порог хуже отказа старта.

**Чанки без заголовков в начале**
Клиент забрал не то поле ответа. `_extract_texts` в `app/docling/client.py`
перебирает `contextualized_text` → `text` → `raw_text`, потому что имя поля
различается между версиями. Прогони один документ, посмотри на выход и поправь
порядок ключей. Полная схема всегда на `/docs` живого сервера — она авторитетнее
любой документации, включая эту.

**Границы чанков не совпадают с ожиданиями**
Не передан `chunking_tokenizer`, и HybridChunker считает токены дефолтным
токенизатором. Он должен совпадать с эмбеддером — отсюда
`ChunkingOptions(tokenizer="BAAI/bge-m3")`.

**Circuit breaker при bulk-загрузке**
Мало heap или исчерпан off-heap под HNSW. Подними `-Xmx` и проверь
`knn.memory.circuit_breaker.limit`.

**Чат тормозит во время заливки корпуса**
Оба сценария делят один экземпляр модели. Включи
`INGEST_SEPARATE_QUERY_EMBEDDER=true`.

**Изображения не приходят из чанк-эндпоинта**
Известное ограничение: ссылки на ассеты не возвращаются даже при
`include_images=true`. Если нужны картинки — отдельный вызов `/v1/convert/*` с
`image_export_mode=referenced`.

**Настройки OCR не влияют на результат**
Параметр `ocr_engine` в некоторых версиях объявлен устаревшим в пользу
`ocr_preset` и `ocr_lang`. Актуальный список — на `/docs` живого сервера.
